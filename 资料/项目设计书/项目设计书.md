# HarmonyOS 智慧客房 App 项目设计书

## Context

本项目是"智慧客房"课程实训作业。目标是基于 HarmonyOS SDK 6.0.2 (API 22) 开发一个酒店客房控制 App，让住客通过手机/平板/折叠屏远程控制客房内的灯光、空调、窗帘等设备，并请求清理、请勿打扰、SOS 等服务。

当前项目是 DevEco Studio 生成的脚手架（仅包含 Hello World 页面和 80+ 张 UI 资源图片），需要从零搭建完整功能。

## 一、技术架构

### 1.1 整体架构：MVVM + V2 状态管理

```
View (ArkUI @Component)──观察──>ViewModel (@Observed/@State)──调用──>Model (数据+Mock API)
  ↑                                                                  │
  └────────────────── 数据绑定 (@Link/@Prop/@Consume) ────────────────┘
```

**各层职责：**
- **Model**：数据实体（RoomState, DeviceInfo, AirConditioner, Light, Curtain, Service）+ Mock API Service
- **ViewModel**：持有 @State 状态，封装业务逻辑，调用 Model 层 API
- **View**：纯 UI 渲染，通过 @Prop/@Link/@Consume 绑定 ViewModel 状态

### 1.3 V2 状态管理装饰器使用规范

| 装饰器 | 用途 | 典型场景 |
|--------|------|---------|
| `@State` | 组件内状态 | 页面/组件的自身状态 |
| `@Prop` | 父→子单向传递 | 父组件传数据给子组件（只读） |
| `@Link` | 父→子双向绑定 | 开关状态、温度值等需要回传 |
| `@Provide/@Consume` | 跨层级共享 | Token、房间号、全局设备状态 |
| `@Observed/@ObjectLink` | 嵌套对象响应 | RoomState 中嵌套的空调/灯光对象 |
| `@Watch` | 状态变化回调 | 温度变化触发 API 调用（防抖） |

### 1.4 Navigation 导航架构

```
NavPathStack
  ├── LoginPage           (entry, 不需认证)
  └── MainPage            (需认证)
      ├── HomePage         (Tab 1)
      ├── LightPage        (Tab 2)
      ├── CurtainPage      (Tab 3)
      └── ServicePage      (Tab 4)
```

- **登录页**：独立 NavPath，登录成功后 push MainPage 并清除登录页回退栈
- **主页**：使用 Tabs + TabContent 实现底部 4 Tab 切换（首页/灯光/窗帘/服务）
- **各功能页**：嵌套在各自的 TabContent 内，支持 Navigation 子页面跳转

## 三、数据流设计

### 3.1 全局状态管理

```
AppStateManager (@Observed)
├── isLoggedIn: boolean              // 登录状态
├── token: string                    // 认证 token
├── roomNo: string                   // 当前房间号
├── roomState: RoomState             // 客房完整状态
│   ├── airConditioners: AC[]        // 空调列表
│   ├── lights: Light[]              // 灯光列表
│   ├── lightModes: LightMode[]      // 灯光模式列表
│   ├── curtains: Curtain[]          // 窗帘列表
│   ├── services: Service[]          // 服务列表
│   └── stateFlags: StateFlags       // 状态标识（wurao/qingli等）
```

### 3.2 数据流向

```
App启动 → LoginPage
  │
  ├─ 登录成功 → 保存 token → @Provide AppStateManager
  │
  └─ MainPage (TabBar + Navigation)
      │
      ├─ HomePage  ←→ HomeViewModel  ←→ MockApiService
      │    ├─ @Consume roomState (室温、模式)
      │    └─ @Watch 温度变化 → 防抖 → 调用 setTemp
      │
      ├─ LightPage ←→ LightViewModel ←→ MockApiService
      │    ├─ @Consume roomState.lights (独立灯光状态)
      │    └─ 场景模式切换 → 调用 setLightMode
      │
      ├─ CurtainPage ←→ CurtainViewModel ←→ MockApiService (本地 state)
      │    └─ 窗帘状态本地管理 (@State)
      │
      └─ ServicePage ←→ ServiceViewModel ←→ MockApiService (本地 state)
           └─ 服务状态本地管理 (@State)
```

**字段取舍说明**：`getState` 响应中包含 30+ 个字段。本项目**使用**的字段：

### 5.1 断点系统（Breakpoint System）

| 设备类型 | 宽度范围 | 布局策略 |
|----------|---------|---------|
| 手机 | < 600vp | 单列纵向，Tab 底部导航 |

### 5.2 适配策略

- 使用 `@StorageLink('currentBreakpoint')` 监听当前断点

- product 层提供不同设备的 MainLayout 组装方案
- 资源文件使用 `resources/phone/` `resources/tablet/` 按设备加载

### 5.3 具体适配

- **手机**：标准纵向布局，底部 4 Tab
- **平板**：左侧垂直 Tab 导航（图标+文字），右侧内容区域；灯光模块使用 Grid 2列布局
- **折叠屏展开**：类似平板布局，屏幕更大时可展示更多信息（如首页同时显示空调控制+场景模式+服务状态）

## 七、关键实现细节

### 7.1 空调温度防抖

`common/utils/DebounceUtil.ets`：温度调整使用 500ms 防抖，连续点击 +/- 时只在最后一次操作后发送请求。

### 7.2 Token 持久化

使用 `@kit.ArkData` 的 `preferences` API 存储 token：
- 登录成功 → 保存 token
- App 启动 → 检查 token → 有效则跳过登录页
- 退出登录 → 清除 token

### 7.3 错误处理

统一错误码映射与处理策略（基于接口文档错误处理章节）：

| 错误场景 | HTTP 状态码 / 业务码 | 处理行为 |
|---------|---------------------|---------|
| 请求成功 | `code: 0` / HTTP 200 | 正常返回数据 |
| Token 失效 / 未授权 | HTTP 401 | 清除本地 token → 跳转登录页 |
| 权限不足 | HTTP 403 | Toast "权限不足，请联系前台" |
| 接口不存在 | HTTP 404 | Toast "服务暂不可用" |
| 服务器内部错误 | HTTP 500 | Toast "服务器繁忙，请稍后再试" |
| 登录失败 | 业务 `code: 1` | Toast `msg`（如"客房号或用户名错误"） |
| 设备控制失败 | 业务 `code: 1` | Toast `msg`（如"设备离线或无响应"） |
| 请求参数错误 | 业务 `code: 1` | Toast `msg`（如"参数格式不正确"） |
| 网络超时（10s） | 无响应 | Toast `$r('app.string.common_network_error')` |

实现位置：`common/api/ApiService.ets` 中统一封装 `httpRequest`，在 `response` 拦截器中按上表分发处理。

### 9.2 Git 提交规范

#### Commit Message 模板

```
<type>(<scope>): <subject>

<body>

<footer>
```

#### Type 定义

| Type | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | 修复 bug |
| `test` | 添加/修改测试 |
| `refactor` | 重构（不改变功能） |
| `docs` | 文档变更 |
| `style` | 格式调整（不影响代码运行） |
| `chore` | 构建/工具/依赖变更 |

#### Scope 定义

| Scope | 说明 |
|-------|------|
| `common` | 通用层 |
| `login` | 登录模块 |
| `nav` | 导航框架 |
| `home` | 首页模块 |
| `light` | 灯光模块 |
| `curtain` | 窗帘模块 |
| `service` | 服务模块 |
| `product` | 多设备/产品层 |
| `test` | 测试代码 |
| `config` | 项目配置 |

#### 提交流程

1. 模块代码开发完成 → 单元测试通过 → 插桩测试通过

3. `git add <相关文件> reports/<模块文件夹>/`
4. 按模板编写 commit message → `git commit`
